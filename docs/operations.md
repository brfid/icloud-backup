# Operations

Use this document for installation discovery, updates, normal commands, and alerts. The configuration schema belongs to [configuration](configuration.md); backup mechanics belong to [architecture](architecture.md). Machine-specific status belongs in the private installation, not in repository documentation.

## Identify the active installation

```sh
~/bin/icloud-backup status --json
```

Read `state.installation.config`, `program`, `watchdog`, `interpreter`, and `labels` in that output. They record the actual configuration path, installed files, Python command, and two job labels. The first label is the installer's base label. `state.sources` and the selected configuration describe actual coverage; do not infer it from the example. `version` identifies the invoked runner, while `state.installation.version` records the last installation.

If the installed command or status is broken, inspect `~/bin/icloud-backup` and the matching `~/Library/LaunchAgents/*.plist` files for their explicit program/configuration arguments. The default private state file is under the support directory shown below, but a custom `runtime.state_dir` can move it. Discover the selected config before assuming that default. Do not replace the installation merely because the development checkout moved or disappeared.

| Artifact | Owner and effect |
| --- | --- |
| This Git checkout, wherever cloned | Editable source and documentation; changing it does not replace installed programs |
| `example.config.toml` in the checkout | Portable configuration example only |
| The selected private TOML file | Live source, exclusion, retention, and runtime policy; read at invocation |
| `~/Library/Application Support/icloud-backup/runtime/` | Installed copies of `icloud_backup.py` and `watch.py`; generated by the installer |
| `~/bin/icloud-backup` | Generated shortcut to the installed runner with the selected config |
| `~/Library/LaunchAgents/<label>.plist` and `<label>-watch.plist` | Generated user jobs pointing to installed copies, never the checkout |
| `<state_dir>/state.json` | Private installation metadata, repository identity, and last run/source status |
| `<state_dir>/commands/` and `run.lock` | Recent command logs and local operation exclusion |
| `<cache_dir>` | Disposable metadata cache; no unique recovery data |
| `<dest_root>/restic-v2/` | Actual Restic backup store, including indispensable `config`, `keys`, snapshots, and data |
| `<dest_root>/restic-v2-recovery/` | Exported recovery guide and configuration copy, refreshed at installation |
| `~/Library/Application Support/icloud-backup/migration/` | Private copies of replaced installation files for manual rollback |

Defaults and configurable local paths are listed in [configuration](configuration.md#runtime-options). Editing installed copies directly is temporary: the next installation replaces them from the checkout. The cache and status files cannot replace the backup store, and the recovery configuration does not control scheduled backups.

## Update an existing installation

1. Discover the active configuration and base label as above. Check for an active operation before deployment; installation unloads the selected jobs and may interrupt one.
2. Edit and validate the source checkout. An ordinary Markdown edit does not require deployment. Changes to installed Python files or `RECOVERY.txt` need installation to reach their copies.
3. From the checkout, run the following with the discovered values:

```sh
python3 install.py --config /absolute/path/to/config.toml --label BASE_LABEL
~/bin/icloud-backup status
```

Do not add `--initialize` for an ordinary update. It is for registering a new backup store. Preserve a custom base label: the default `local.icloud-backup` is not an alias for an existing differently named pair, and choosing another label would add another pair of jobs. The installer deliberately re-enables the selected labels if a previous `launchctl disable` remains in effect.

Installation saves previous private files, validates the new plists, replaces the stable copies/shortcut, refreshes the recovery export, records installation metadata, and reloads the jobs. It verifies an existing registered store's identity rather than creating a replacement. It may start a due backup. File replacement and scheduler loading are not one transaction; if installation reports an error, inspect status and its saved migration files, correct the cause, and rerun with the same arguments. No backup data is deleted by installation.

To compare deployed code with a checkout after an update, compare the two Python files against the `program` and `watchdog` paths in installation metadata. The metadata records a version and time, not a Git commit or proof that a checkout is deployed. Do not infer deployment from a clean Git working tree.

## Commands and restoration

| Command | Effect |
| --- | --- |
| `icloud-backup status` / `status --json` | Read local health and installed-job status; no backup-store data scan |
| `icloud-backup snapshots` | List this app's completed snapshots by ID, time, and source |
| `icloud-backup run` | Force a backup cycle, including checks and eligible retention |
| `icloud-backup tick` | Back up only when due; used by the scheduler |
| `icloud-backup verify` | Check backup-store structure |
| `icloud-backup verify --full` | Read and check all stored data |
| `icloud-backup watch` | Manual compatibility check with alerts; the scheduled independent watchdog is `watch.py` |

Prefix commands with `~/bin/` if that directory is not on your shell's search path. Config selection follows [the documented precedence](configuration.md#changes-and-precedence). A separate verification command does not create a backup or mark missing sources protected.

```sh
icloud-backup restore projects --snapshot SNAPSHOT_ID --target "$HOME/Downloads/recovered-projects"
```

Use a configured source name and a snapshot ID from `snapshots`; omit `--snapshot` for the latest completed point. Short IDs must be unambiguous. The target must be new or empty and outside all sources, backup storage, state, and cache. Restore uses the original path recorded in the selected snapshot even when the configured source path changed, and verifies restored data. Select a snapshot preceding deletion to recover a deleted file.

For a source no longer configured, or recovery without this installation, follow [RECOVERY.txt](../RECOVERY.txt) to use Restic directly. That is the sole owner of the independent recovery command sequence. The installer copies it beside the backup store so it remains available without the original Mac or this Git checkout.

## Schedule and alerts

The daily job runs at 03:00 local time and login, with hourly due checks. It requests work if no backup covers the most recent local 03:00, the source configuration changed, or the previous run failed. Successful repeated due checks do not make another backup that day. Login/wake checks catch up missed work when the account next runs; they do not operate while the Mac is off or logged out.

The independent watchdog runs at login and every six hours. It checks the runner's local status, including missing sources, stale snapshots, changed configuration, interrupted or long-running work, and unloaded jobs. A source more than 36 hours stale is a problem. The watchdog writes the configured warning file and attempts a macOS notification; notifications depend on system settings. A backup cycle that succeeds for all sources clears the warning.

The watchdog can report a missing or broken runner because it does not import it. It still needs Python, a running Mac/account, and its own installed job. If all jobs are removed, a manually invoked status command can reveal that, but no local scheduled checker can alert on its own. Allow required macOS source access if prompted, and verify that the scheduled run covers every configured source.

Logs are `~/Library/Logs/icloud-backup.log` and `~/Library/Logs/icloud-backup-watch.log`; the most recent 40 individual engine logs are under the configured state directory. Private logs/status may contain source paths and filenames. Keep them outside Git and redact them before sharing an issue. iCloud upload progress and quotas are intentionally outside these checks; handle sync problems through iCloud.

### Cloud-only reads and permission prompts

For `resource deadlock avoided` errors, first check that the installed runner includes the explicit download-on-read policy described in [architecture](architecture.md#icloud-and-space), then inspect iCloud availability and the exact failing path. Finder's Download Now on the backup store can recover an immediate run. Validate fixes through the actual scheduled job using `launchctl kickstart gui/$(id -u)/BASE_LABEL` and wait for fresh success for every source; a successful command launched from a terminal does not establish the scheduler's access.

macOS attributes the scheduled job's permissions to its Python interpreter. In System Settings > Privacy & Security > Files & Folders, check its iCloud Drive access and Desktop access for the warning file. A Python upgrade can create a new interpreter identity and require renewed approval. A Desktop prompt after a failure can be from writing the alert, rather than the cause of the backup failure; compare log times before diagnosing it. Do not grant Full Disk Access merely to fix download policy. The runner still requires ordinary macOS authorization for protected files.

An `Expecting value` JSON error after successful Restic retries can indicate an older runner mixing diagnostic stderr with JSON stdout. Version 2.0.1 separates those streams. Update from the corrected source using the existing configuration and labels, then retry; do not initialize a new store or remove its keys.

## Connect, migration, and stopping

For an existing backup store on a replacement Mac, first use the recovery guide if files are needed immediately. To resume this app, configure the new paths and run `python3 icloud_backup.py --config /absolute/path/to/config.toml connect` from the checkout, then install without `--initialize`. `connect` reads and checks all data before registering the store locally; it does not infer source configuration from snapshots or reconstruct old status. The next backup establishes current per-source status. Keep one Mac as the writer.

The old archive implementation remains in Git history. The Restic store uses a separate child directory and leaves legacy `.tar.gz` archives elsewhere under the destination untouched. Extract an old archive into a separate empty folder using standard archive tools; retain legacy archives until their recovery is independently demonstrated.

To stop scheduling, unload each actual label with `launchctl bootout gui/$(id -u)/LABEL`. Bootout unloads the job now; remove its plist to prevent loading on a later login, or deliberately disable the label if that is the intended persistent state. Reinstallation enables and loads the selected labels again. Stopping jobs or removing the runtime/shortcut does not delete the backup store. Preserve the private configuration and exported recovery instructions before uninstalling. Migration copies are rollback material, not an automatic rollback mechanism.
